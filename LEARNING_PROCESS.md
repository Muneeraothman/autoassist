# How I'm Learning This Project

A standing agreement for how each phase should go, since I'm new to all of this and want to actually master the concepts, not just end up with a repo I can't explain.

## The pattern, every phase:

1. **Before new material** — get a plain-language explanation first, no assumed knowledge. If an analogy helps it click, that gets saved into GLOSSARY.md.
2. **While building** — I do the actual typing. Each command gets explained piece by piece before I run it, not just handed to me to paste blindly.
3. **End of every phase — mandatory review before moving on:**
   - Quiz me on everything from that phase, one question at a time
   - Anything I get wrong or say "I'm not sure" to gets re-explained immediately, not glossed over
   - Last step: explain one concept back in my own words, unprompted (no multiple choice) — this is the real test, closer to what an interviewer would actually ask
4. **After the review** — update GLOSSARY.md (new terms explained fully) and JOURNAL.md (what happened, what I learned, what was shaky and got fixed)
5. **Do not start the next phase until this review has happened.** This is a hard checkpoint, not optional.

## Why

The build guide's own philosophy is "learn each piece right before you use it, then build" — this just adds a checkpoint at the end of each phase to confirm the learning actually happened, instead of assuming it did because the code works.
